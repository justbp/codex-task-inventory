# `smart_approval_agent` 圆桌讨论结论

更新日期：2026-08-12
讨论对象：`/Users/wangfei/Developer/smart_approval_agent`
讨论流程：独立调查 → 匿名交叉质询 → 独立主持综合

## 议题

项目目前给人的直接感受是维护困难、智能程度不足，并依赖较多 Tool。本轮讨论的目的不是接受这一描述，而是检查问题定义是否成立，寻找可替代架构、工程方案、开源实现与研究方向，并明确哪些判断仍缺证据。

## 核心结论

“大量 Tool 导致系统不智能和难维护”不是准确的问题定义。

模型表面看到的报销 Tool 只有 6 个，但 `apply_reimbursement_actions` 内含 11 类动作，因此不能只按顶层 Tool 数量评估复杂度。当前证据更支持下面的问题定义：

> 业务协议分散在 Skill、Tool schema、Runner 中间件、Service 和领域 Graph 多层；模型表面负责选择能力，Runner 又会改写模型决定，而领域 Graph 最后执行确定性流程。维护困难主要来自协议所有权和状态恢复边界不清，而不是简单的 Tool 数量。

现阶段不应立即去 Agent 化，也不应仅通过更换 Deep Agents、LangChain、LangGraph 或 Temporal 得出架构已经改善。应先建立可度量的生产等价评测，再用业务终态数据比较候选路线。

## 已有证据支持的判断

### 1. 有效命令空间比顶层 Tool 数量更重要

- 报销业务公开 6 个顶层 Tool。
- 一个批量动作 Tool 内部包含 11 类 Action。
- 真正需要测量的是当前状态下合法命令、Schema 宽度、调用顺序、隐藏副作用及模型选择错误，而不是只数 Tool。

### 2. 业务协议散落在多层

- Skill 用自然语言规定严格调用顺序。
- Runner 注入或替换模型 Tool Call，并包含银行短信、提交审阅等报销专属逻辑。
- Tool 层仍会补充业务默认值。
- 领域 LangGraph 另有动作、校验、人审和提交 Saga。
- `service.py` 与 `workflow.py` 存在重复的外部端口 Protocol。
- 领域动作文件同时承担大量中文展示文案。

这意味着一次用户故事的修复可能同时影响 Prompt、Skill、Tool、Runner、Service、Graph、Store、展示和测试。

### 3. 外层 Agent loop 与内层业务 Graph 同时存在

两层编排并存已经证实，但尚不能直接断言它们完全重复。合理的分层可能是外层负责语言与会话，内层负责资金安全与提交 Saga。需要通过协议所有权矩阵证明同一业务不变量是否在多层重复表达。

### 4. Checkpoint/HITL 耦合已有真实事故证据

普通会话与提交 HITL 共用 checkpoint/thread，会扩大 checkpoint 损坏的影响。当前异常恢复还依赖第三方异常文本指纹，这是比泛泛讨论框架优劣更直接的可靠性证据。

### 5. 当前评测不足以裁决架构

- 真实模型评测只有 8 个 case。
- 评分偏重 Tool 名和禁用短语。
- 评测使用 Recording Tools 和简化 Prompt，不是完整生产 Runner、Skill 和 Tool contract。

因此尚不能证明 Deep Agents 是主要问题，也不能证明去 Agent 化、拆分或合并 Tool 会提高业务完成率。

### 6. Redis 更新存在理论并发覆盖窗口

业务状态采用读后整对象覆盖，没有通用 revision CAS。这证明存在风险，但本轮没有证据证明生产中已经发生静默丢更新，因此优先级需要并发实验裁决。

## 尚未证实的问题

- “智能不足”具体指错误命令、漏调用、澄清过多、处理中途纠正失败、回复僵硬、延迟高，还是误提交。
- 真实端到端成功率、误提交率、重复提交率和各类失败分布。
- Runner 改写模型 Tool Call 的命中率及误改写率。
- Deep Agents 自身贡献了多少 Token、延迟、状态和故障面。
- 双编排到底是合理分层还是同一协议的重复实现。
- 独立 `review_id` 能减少多少复杂度，还是仅把复杂度迁移到 review store。
- revision CAS 是否对应当前真实缺陷。
- `ApprovalService.resume()` 是否确属死代码；目前只能说仓库内生产路径未发现引用，可能仍是外部兼容入口。
- Temporal、Event Sourcing、完整 Outbox 或联邦领域架构是否值得其迁移和运维成本。
- 当前是否真的存在第二、第三个独立写领域与组织边界，足以支撑通用 Agent 平台方向。

## 主要分歧

### 模型应拥有多少流程控制权

1. 模型只输出 `IntentPatch`、纠正和指代解析，确定性 reducer 控制状态转移。
2. 保留 Agent tool-loop，但只暴露当前状态下合法的命令。
3. 在低风险语言理解任务上减少护栏，利用更强模型；资金、权限和提交边界仍由确定性协议控制。

### 两层编排是否应统一

一方认为外层负责语言、内层负责业务 Saga 是合理分层；另一方认为确认、恢复和合法顺序已泄漏到 Skill、Runner 和 Graph 多处。需要按具体用户故事追踪，而不是根据文件数量裁决。

### 先修事故还是先补测量

Checkpoint/HITL 解耦有事故支持；生产等价评测和协议矩阵则能避免只把复杂度搬家。较稳妥的方式是先做不改变生产结构的故障原型和回放，再决定迁移。

## 候选路线

### A. 受限 Agent

让确定性领域核返回：

```json
{
  "revision": 17,
  "blockers": [],
  "allowed_commands": [],
  "state_projection": {},
  "next_ui": {}
}
```

模型只能从当前 revision 的合法命令中选择。日志同时记录“当时允许什么”和“模型选择了什么”，以区分投影错误和模型错误。

### B. `IntentPatch` 加确定性工作流

模型把自然语言编译成结构化意图、字段补丁和证据引用；确定性 reducer 处理权限、校验、状态变化和提交。对依赖外部查询的候选选择，允许受限的“查询—投影—澄清”循环，不能假设一次抽取闭合全部流程。

### C. 简化为普通 LangChain Agent

保留粗粒度 Tool 和领域核，替换 Deep Agents Harness。成功标准不是构造函数更简单，而是实际删除了多少业务特例、状态和故障面，同时保持 HITL 恢复率。

### 可独立验证的小改进

- 建立独立的 `review_id`/`operation_id` 索引，覆盖重复确认、旧确认、重启、checkpoint 损坏和提交超时。
- 将飞书按钮与 `review_id + revision/digest + 幂等键` 作为完整协议实验。
- 将展示投影从金额和状态机核心分离。
- 合并重复 Protocol，调查疑似遗留入口的真实调用情况。
- 只对提交故障窗口实验最小 Outbox，不直接扩张到完整事件溯源。
- 高风险歧义主动询问或使用强类型交互，低风险语言歧义交给模型处理。

## 建议的下一步

1. 定义“智能”的业务指标：终态正确率、澄清轮数、非法命令、Runner 改写次数、误提交/重复提交、外部调用数、Token、p95 延迟和恢复结果。
2. 对“银行短信发起”“修改后提交”“待确认时取消或再次修改”制作协议所有权矩阵。
3. 建立生产等价回放：复用真实 Runner、Skill、Tool contract 和状态逻辑，只 fake LLM 与外部端口，断言最终业务状态和外部调用次数。
4. 分离两类评测：固定模型输出的可重复契约测试，以及少量真实模型重复运行的统计评测。
5. 做两个故障原型：并发旧版本写入验证 CAS；独立 `PendingReviewStore` 验证 HITL 解耦。
6. 使用同模型、同场景比较三个 Shadow 方案：当前 Deep Agent、`create_agent + allowed_commands`、`IntentPatch + 确定性 Graph`。
7. 后续外部检索只回答明确问题，例如 LangGraph checkpoint 生产恢复契约、Action union 的工具选择错误、Temporal HITL Saga 改造成本，以及开源审批系统的旧审批与幂等协议。

## 本轮 Agent 表现与证据限制

- Cursor 提供了最广的代码考古和候选方向，但本轮联网被拒绝，部分外部类比只是待验证线索，并曾将“仓库内未引用”过度表述为“死代码”。
- Codex 的研究更注重证据边界，交叉质询有效纠正了多项过度推断，但首次研究调用超时，重试后才完成，成本和时延偏高。
- Codex 主持人能够保留分歧、剔除无效证据，并形成可证伪的下一步。
- MiniMax 本轮因 Claude CLI `plan` 权限模式与无工具角色冲突，只返回流程性话语。其席位没有形成有效技术观点，不能作为第三票；这属于接入配置问题，不是对模型能力的结论。

## 主持结论

当前最稳健的方向不是立即去 Agent 化或更换框架，而是：

> 先测出分散的业务协议和真实失败分布；并行验证状态投影与 review 故障隔离，再依据业务终态正确率、误提交率和恢复率，决定模型应选择命令，还是只负责编译语义。
