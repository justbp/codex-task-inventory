# Codex Workbench 产品与上下文设计

状态：Draft v0.2  
日期：2026-08-07

## 1. 产品目标

把当前的 Codex 任务监控看板扩展为个人工作控制台：

- 用户负责目标、价值取舍、高风险审批和最终验收。
- Codex 负责整理、调研、执行、验证、总结和提出建议。
- 看板负责任务记忆、流程约束、上下文组装、运行关联和审计。

产品必须让用户平时通过看板掌握工作，只在需要深入讨论时进入具体 Codex 对话。

## 2. 核心概念

### 2.1 Work Item（工作任务）

长期存在的工作实体，是工作的事实来源。它不依赖某个 Codex 对话是否存在或是否归档。

至少包含：

- 标题与目标结果。
- 当前阶段。
- 工作状态。
- 下一步唯一动作。
- 验收标准。
- 约束与风险边界。
- 当前结论与恢复点。
- 任务关系。
- 版本号与审计信息。

### 2.2 Run（执行记录）

一次具体的 Codex 执行。一个 Work Item 可以有零个、一个或多个 Run。

每个 Run 记录：

- 对应的 Codex thread 和 turn。
- 本次执行目标与允许范围。
- 开始时使用的上下文版本。
- 运行状态、进展、决策请求和执行结果。
- 验证证据、剩余风险和结束原因。

### 2.3 Board Manager（看板管家）

跨任务的管理型 Codex 能力，只负责整理、分析和提出看板变更建议，不负责执行具体任务。

默认采用临时调用，每次从看板读取经过筛选的最新摘要。只有需要持续讨论工作策略时，才创建独立的看板管家对话。

## 3. 产品不变量

后续设计与实现不得破坏以下约束。

### I-01：工作任务是事实来源

Work Item 是目标、状态、验收标准、决策和恢复上下文的唯一事实来源。Codex 对话不是任务数据库。

### I-02：任务与对话必须分离

任务可以在没有 Codex 对话时存在。启动执行时为任务创建或关联 Run；删除、归档或更换对话不得导致任务上下文丢失。

### I-03：一个独立问题保留一个主对话

不同结果目标使用不同主对话。同一问题优先继续原主对话；需要新对话时，新 Run 仍必须关联原 Work Item。看板管家对话不得承担具体任务执行。

### I-04：每次执行都从看板重建上下文

Codex 开始或恢复任务时，必须读取 Work Item 的最新版本、相关决策、验收标准、关系和恢复点。系统不得假设某个对话仍记得完整上下文。

### I-05：工作状态与运行状态分离

工作状态描述任务在流程中的位置；运行状态描述 Codex 当前是否运行。两者不得使用同一个字段表达。

### I-06：用户拥有价值判断权

今日主线、业务优先级、风险取舍、范围扩大、生产操作和最终验收由用户决定。Codex 可以提出有证据的建议，不能替用户确认。

### I-07：Codex 不能自行完成任务

Codex 完成执行和自验证后只能提交待验收。只有用户明确确认，Work Item 才能进入 Done。

### I-08：未知问题先探索

缺少清晰目标、关键假设未验证或验收标准无法定义时，系统不得把任务包装成长时间实现任务。可以启动只读探索 Run，输出问题定义和方案。

### I-09：暂停必须可恢复

任务暂停、阻塞或切换主线前必须留下恢复点：当前目标、结论、已完成、未解决、下一步唯一动作和相关资源。

### I-10：AI 修改必须可见

看板管家进行合并、拆分、调整主线、改变状态或启动任务前，必须展示变更建议。允许自动执行的内容整理也必须保留审计记录。

### I-11：所有写操作可归因

每次任务、关系、评论、决策和状态修改必须记录 actor、来源 Codex thread、时间和修改前后版本。

### I-12：并发修改不能静默覆盖

Work Item 和评论写入必须带 expected version。发生版本冲突时重新读取、合并或请求用户处理，不能使用最后写入覆盖。

### I-13：外部副作用必须幂等

创建 Codex Run、发送决定、创建生产业务单据等操作必须使用 idempotency key，避免超时重试造成重复执行。

### I-14：看板约束流程，不替代判断

看板可以根据可配置的 WIP 策略警告或阻止继续启动，但不能自行决定哪个业务目标更重要。

### I-15：原始证据与摘要分离

看板保存结构化摘要和证据引用，不把全部对话、日志和测试输出复制进任务正文。需要核实时可以回到原 Run 或原始证据。

## 4. 状态模型

### 4.1 工作阶段 Stage

- `explore`：定义问题、验证假设。
- `experiment`：进行小规模、可逆实验。
- `execute`：执行已批准方案或里程碑。
- `verify`：独立验证结果和验收条件。

### 4.2 工作状态 Work Status

- `inbox`：刚捕获，尚未整理。
- `ready`：目标和下一步明确，可以启动。
- `active`：存在已批准且未结束的工作 Run。
- `awaiting_decision`：需要用户作出业务或风险判断。
- `in_review`：Codex 已提交结果，等待用户验收。
- `blocked`：存在明确阻塞条件。
- `parked`：有价值但当前不推进。
- `done`：用户已确认完成。
- `canceled`：明确不再继续。

### 4.3 Run Status

- `queued`
- `running`
- `waiting`
- `completed`
- `interrupted`
- `failed`
- `canceled`

当前看板的“执行中”“等待我”“中断”来自 Run Status；今日工作台的主线、待验收、停车场来自 Work Status。

## 5. 三方交互协议

完整的真实工作模拟与交互口径见：`docs/CONTEXT_MANAGEMENT_INTERACTION_SPEC.md`。该文档描述目标产品形态，不代表其中所有界面与 Codex 集成都已实现。

### 5.1 捕获

1. 用户输入一句话或从 Codex 对话创建任务。
2. 看板创建 `inbox` Work Item，不强迫用户立即补全字段。
3. Codex 可以生成整理建议，但不自动启动。

### 5.2 整理与计划

1. 用户请求“整理收集箱”或“安排今天”。
2. 看板只提供相关任务摘要、当前 WIP、阻塞和待验收情况。
3. 看板管家返回结构化变更建议及理由。
4. 用户确认涉及主线、状态、拆分、合并和启动的变更。
5. 看板以原子操作应用变更并记录审计。

### 5.3 启动执行

1. 用户从 Work Item 发起执行。
2. 看板执行 readiness 和 WIP 检查。
3. 看板生成不可歧义的 Context Envelope。
4. 看板创建独立 Run，并创建或继续该任务的专属 Codex 主对话。
5. Codex 只在本 Run 的批准范围内工作。

### 5.4 请求决策

1. Codex 提交结构化 Decision Request，而不是只在聊天中等待。
2. 看板把 Work Item 标记为 `awaiting_decision`，展示背景、选项、推荐、风险和默认后果。
3. 用户在看板选择，或进入专属对话深入讨论。
4. 看板记录决定并发送到原 Run。

### 5.5 提交验收

1. Codex 回写完成内容、验证结果、证据引用、剩余风险和建议下一步。
2. Run 结束，Work Item 进入 `in_review`。
3. 用户选择通过、退回、接受当前结果并创建后续任务，或取消。
4. 只有“通过”使 Work Item 进入 `done`。

### 5.6 暂停与恢复

1. Codex 或用户生成 Recovery Point。
2. 看板保存到 Work Item，不只保存在对话中。
3. 恢复时创建新的 Context Envelope；是否继续原对话不影响上下文完整性。

## 6. Context Envelope

每个 Run 启动时必须由看板生成如下上下文。字段为空时显式标记“未提供”，不能依赖 Codex 猜测。

```yaml
context_version: 1
work_item:
  id: TASK-123
  version: 7
  title: ...
  goal: ...
  stage: explore | experiment | execute | verify
  status: ready
  next_action: ...
acceptance:
  criteria:
    - ...
scope:
  allowed: ...
  excluded: ...
  stop_conditions:
    - 关键假设不成立
    - 需要扩大范围或权限
decisions:
  - decision: ...
    reason: ...
constraints:
  - ...
recovery_point:
  current_conclusion: ...
  completed: ...
  unresolved: ...
relations:
  parent: ...
  blocked_by: []
  related: []
run:
  objective: ...
  expected_output: ...
  report_format:
    - 已完成
    - 验证结果
    - 风险
    - 需要用户决定
    - 下一步
```

Context Envelope 必须记录生成时间、Work Item version 和摘要来源。任务发生关键修改后，旧 Run 不自动获得新范围；需要明确发送更新或创建新 Run。

## 7. 看板管家的输入边界

看板管家默认只接收完成当前管理动作所需的最小数据：

- 整理收集箱：收集箱任务及可能重复项。
- 安排今天：候选任务摘要、当前 WIP、等待决策和待验收情况。
- 分析阻塞：阻塞任务、依赖和最近恢复点。
- 周复盘：本周完成、退回、停滞和验收时长。

不得默认把所有任务全文、所有 Codex 对话和全部执行日志放进一个管理对话。

## 8. 权限边界

### Codex 可自动执行

- 查询、汇总和识别停滞。
- 生成任务摘要、恢复点和验收报告草案。
- 补充不改变业务含义的结构化内容。
- 记录自身 Run 的进展和验证证据。

### Codex 必须先提交变更建议

- 合并或拆分任务。
- 改变主线、优先级和 Work Status。
- 启动新的 Run。
- 改变目标、范围和验收标准。

### 必须由用户明确确认

- 标记 Work Item 为 Done。
- 扩大权限、预算或修改范围。
- 不可逆操作和生产数据修改。
- 业务价值和风险取舍。

## 9. 视图边界

### 现有任务看板

继续以 Codex Run 的真实运行状态为中心，保留当前清晰的监控体验。它回答：Codex 现在在做什么？

### 今日工作台

以 Work Item 和人的注意力为中心，展示今日主线、后台执行、等待决定、待验收和停车场。它回答：我现在应该关注什么？

### 任务详情

作为两个视图共享的事实入口，展示 Work Item 内容、Run 历史、决策、验证证据和恢复点。

## 10. 可配置策略，不属于不变量

以下内容可以根据使用反馈调整：

- 今日主线默认上限 1。
- 后台 Run 默认上限 2。
- 待验收默认上限 2。
- 哪些内容整理允许 Codex 自动应用。
- 看板管家使用临时调用还是长期对话。
- 卡片布局、列顺序、通知方式和默认首页。

无论策略如何调整，都不得破坏第 3 节的不变量。

## 11. 实施里程碑

里程碑必须按顺序推进。每个里程碑都是可独立验收的结果，不允许为了提前展示后续功能而绕过当前里程碑的约束。

### M0：建立现有看板行为保护网

**目标**

在引入新模型前，明确并保护当前任务看板已有的运行监控行为。

**交付物**

- 记录当前数据库表、API、状态映射和手工任务启动流程。
- 为“执行中、等待我、待 Review、人工通过、再次执行后重新 Review”补齐回归测试。
- 固定现有任务看板的接口契约，后续通过适配层演进，避免直接重写页面。
- 明确旧数据迁移和回滚方案。

**验收条件**

- 当前看板功能和交互没有可见变化。
- 现有数据可完整读取。
- 核心状态行为有自动化测试保护。
- 新数据库迁移失败时可以恢复到迁移前状态。

**保护的不变量**

- `I-05` 工作状态与运行状态分离。
- `I-07` Codex 不能自行完成任务。
- `I-15` 原始证据与摘要分离。

### M1：建立 Work Item 与 Run 基础模型

实施记录：`docs/M1_WORK_ITEM_RUN_MODEL.md`

**目标**

让工作任务成为独立事实来源，并把 Codex Thread 降为一次执行记录。

**交付物**

- 新增 `work_items`、`runs`、`audit_events` 和幂等请求记录。
- Work Item 具有独立 ID、version、Work Status 和基础字段。
- Run 关联 Work Item、Codex thread、turn 和 Run Status。
- 一个 Work Item 支持零个或多个 Run。
- 提供带 `expected_version` 的 Work Item 和 Run API。
- 把现有手工任务和线程元数据迁移或映射到新模型。

**验收条件**

- 可以创建没有 Codex Thread 的 Work Item。
- 可以为同一 Work Item 创建两个 Run，且不会生成两个工作任务。
- 并发使用旧 version 修改同一任务时返回冲突，不发生静默覆盖。
- 重复提交相同幂等键不会创建两个 Run。
- 每次写入都能查到 actor、thread、时间和版本变化。

**保护的不变量**

- `I-01` 工作任务是事实来源。
- `I-02` 任务与对话必须分离。
- `I-05` 工作状态与运行状态分离。
- `I-11` 所有写操作可归因。
- `I-12` 并发修改不能静默覆盖。
- `I-13` 外部副作用必须幂等。

### M2：实现上下文生成、暂停与恢复

实施记录：`docs/M2_CONTEXT_RECOVERY.md`、`docs/M2_CODEX_EXECUTION_BRIDGE.md`

**目标**

保证任何新 Codex 对话都能仅依靠看板中的最新任务信息继续工作。

**交付物**

- 为 Work Item 增加目标、阶段、下一步、验收标准、范围、停止条件和约束。
- 增加 Decision、Recovery Point、关系和证据引用。
- 实现版本化 Context Envelope 生成器。
- 启动 Run 时保存本次使用的 Context Envelope 快照。
- 对不成熟任务执行 readiness 检查，并支持转换成只读探索 Run。
- 暂停、阻塞和切换主线时生成并保存 Recovery Point。
- 通过最小 API 幂等创建或恢复真实 Codex thread/turn，并把真实执行位置绑定到 Run。

**验收条件**

- 新对话不读取旧对话全文，也能根据 Context Envelope 准确描述目标、范围、验收标准和下一步。
- 同一任务修改目标后，旧 Run 的范围不会被静默改变。
- 暂停任务后创建新 Run，可以从 Recovery Point 继续。
- 缺少关键目标或验收标准时，系统不会直接启动长时间实现 Run。
- Context Envelope 只包含必要摘要和证据引用，不复制全部日志。

**保护的不变量**

- `I-01` 至 `I-04`。
- `I-08` 未知问题先探索。
- `I-09` 暂停必须可恢复。
- `I-15` 原始证据与摘要分离。

### M3：打通执行、决策与验收闭环

实现进度：M3.1 已完成 Run 终态与 Review Submission；M3.2 已完成 Decision Request 与回答原 Run；M3.3 已完成通过、退回修改、接受当前结果并创建后续任务。M3 后台闭环完成，正式页面交互留在 M4。

实施记录：`docs/M3_1_RUN_REVIEW_LIFECYCLE.md`、`docs/M3_2_DECISION_REQUEST_ROUTING.md`、`docs/M3_3_REVIEW_ACTIONS.md`

**目标**

让具体任务的 Codex 可以通过看板结构化汇报、请求决定和提交验收。

**交付物**

- Codex Run 结构化回写进展、验证证据和剩余风险。
- 实现 Decision Request，并准确路由用户回答到原 Run。
- 实现 Review Submission：已完成、验证结果、证据、风险和建议下一步。
- 用户支持验收通过、退回修改、接受当前结果并创建后续任务。
- 保持现有任务看板以 Run Status 展示真实 Codex 运行状态。

**验收条件**

- Codex 等待决定时，看板能展示对应 Decision Request，回答不会发送到错误对话。
- Run 完成后 Work Item 进入 `in_review`，不能直接进入 `done`。
- 只有用户明确通过验收，Work Item 才进入 `done`。
- 退回修改会创建或继续该 Work Item 的 Run，不会复制 Work Item。
- 当前任务看板的运行监控体验保持不变。

**保护的不变量**

- `I-03` 一个独立问题保留一个主对话。
- `I-05` 至 `I-07`。
- `I-11`、`I-13` 和 `I-15`。

### M4：新增“今日工作台”视图

实现进度：M4.1 已完成独立今日工作台和用户手工主线；M4.2 已完成统一任务详情与 Decision/Review 页面交互；M4.3 已完成可配置 WIP 策略、超限提醒与启动限制。

实施记录：`docs/M4_1_TODAY_WORKSPACE.md`、`docs/M4_2_WORK_ITEM_DETAIL.md`、`docs/M4_3_WIP_POLICY.md`

**目标**

在不改变现有任务看板定位的前提下，提供面向人的注意力和工作结果的管理视图。

**交付物**

- 新增“今日工作台”，保留现有“任务看板”。
- 展示今日主线、后台执行、等待决定、待验收和停车场。
- 任务详情统一展示 Work Item 内容、Run 历史、Decision、Review 和 Recovery Point。
- 实现可配置的 WIP 策略和超限提醒。
- 第一版由用户手工确定主线和计划，不依赖看板管家 AI。

**验收条件**

- 用户无需打开 Codex 对话就能知道今天关注什么、需要决定什么、需要验收什么。
- 同一任务在今日工作台展示 Work Status，在任务看板展示 Run Status，两者不冲突。
- WIP 超限会提示或按配置阻止启动，但不会擅自替用户选择主线。
- 现有任务看板仍可独立使用。

**保护的不变量**

- `I-05` 工作状态与运行状态分离。
- `I-06` 用户拥有价值判断权。
- `I-07` Codex 不能自行完成任务。
- `I-14` 看板约束流程，不替代判断。

### M5：引入按需看板管家 AI

**目标**

让 Codex 帮助整理和规划看板，同时保持用户控制权和任务上下文隔离。

**交付物**

- 提供“整理收集箱、安排今天、分析阻塞、整理待验收”四个按需动作。
- 每个动作只读取完成任务所需的最小看板摘要。
- 输出结构化变更建议、理由和影响，不直接输出普通聊天作为最终结果。
- 实现变更预览、逐项选择、原子应用和审计记录。
- 管家调用与具体任务 Run 隔离，不在管家上下文中执行任务。

**验收条件**

- 整理收集箱时不会加载所有任务全文和全部 Codex 对话。
- 管家不能自行改变今日主线、启动 Run 或标记完成。
- 用户可以在应用前看到准确的修改前后差异。
- 重复应用同一建议不会造成重复任务或重复 Run。
- 每项 AI 修改都能追溯到建议、确认人和执行调用。

**保护的不变量**

- `I-03` 看板管家不承担具体任务执行。
- `I-06` 用户拥有价值判断权。
- `I-10` AI 修改必须可见。
- `I-11` 至 `I-15`。

### M6：自动整理、提醒与效果验证

**目标**

在按需交互稳定后，增加低风险自动化，并验证产品是否真正改善工作闭环。

**交付物**

- 停滞任务、决策等待和验收积压提醒。
- 每日计划草案和每周复盘草案。
- 可配置的自动内容整理，默认只生成建议或草案。
- 记录恢复耗时、验收时长、返工率和重要任务闭环数量。

**验收条件**

- 自动化失败不会改变任务事实或重复触发外部副作用。
- 自动化不会自行决定主线、扩大范围或通过验收。
- 用户可以关闭每种自动化并查看其历史记录。
- 至少经过一个真实使用周期，确认恢复时间或验收积压等指标得到改善，再扩大自动化范围。

**保护的不变量**

- `I-06`、`I-07`、`I-10`、`I-13`、`I-14` 和 `I-15`。

## 12. 版本边界

### 基础闭环版本：M0 至 M3

完成任务、Run、上下文、决策和人工验收闭环。此时还没有新的今日工作台，也没有看板管家 AI，但底层语义已经可靠。

### 可用产品版本：M0 至 M4

新增今日工作台，用户可以通过看板管理注意力和工作结果。这个版本应先进入真实日常使用。

### AI 管理版本：M0 至 M5

增加按需看板管家，让 Codex 生成可审核的整理和计划建议。

### 自动化版本：M0 至 M6

只有前面版本经过真实使用验证后，才增加定时整理和效果指标。

## 13. 总体验收标准

完整设计最终需要满足：

1. Work Item 可以脱离 Codex Thread 独立存在。
2. 一个 Work Item 可以关联多个 Run。
3. 启动和恢复 Run 时能从看板生成完整 Context Envelope。
4. 当前任务看板的运行监控行为保持不变。
5. Codex 可以结构化回写进展、Decision Request 和 Review Submission。
6. 用户可以在看板回应决定，并准确路由到原 Run。
7. Codex 不能直接把任务标记为 Done。
8. 所有修改都有版本检查和 actor/thread 审计。
9. 新对话在不读取旧对话全文的情况下，可以依靠 Work Item 和 Recovery Point 继续工作。
10. 看板管家只接收必要任务摘要，并通过可审核的变更建议管理看板。

## 14. 后续 Codex 执行前必读

任何实现本设计的 Codex 任务开始前，必须：

1. 完整读取本文件。
2. 声明本次修改涉及哪些不变量。
3. 说明如何验证这些不变量没有被破坏。
4. 如果实现要求改变不变量，停止执行并请求用户确认。
